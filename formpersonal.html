Práctica integradora

FormPersonal: todo junto en un formulario

Última parada del recorrido. En un solo formulario de NetBeans aplicaremos herencia, polimorfismo, clase abstracta, método abstracto e interfaz. Nada nuevo que aprender: solo juntar las piezas de las dos guías anteriores.

Lo que ya sabes y aquí usarás: extends, super(...), @Override, abstract class, abstract en métodos, interface e implements. Si alguno no te suena, repasa las guías de herencia y de clases abstractas antes de continuar.

1. El caso práctico

Una empresa necesita registrar a su personal. Todos los trabajadores comparten los mismos datos básicos:

Dato común Tipo en Java
Nombres String
Apellidos String
DNI String
Dirección String
Sexo String
Sueldo base double

Pero no todos los trabajadores son iguales. Hay docentes y hay administrativos, y cada tipo calcula su pago final de forma distinta: al docente se le suma una bonificación, al administrativo se le resta un descuento.

Personal
      │
      ├── Docente (sueldo + bonificación)
      └── Administrativo (sueldo - descuento)

1.1 ¿Por qué Personal será abstracta?

Piénsalo desde el negocio: cuando la empresa contrata a alguien, contrata a un docente o a un administrativo. Nunca contrata a un «personal genérico». Ese objeto no existe en la realidad.

Además, si intentáramos calcular el pago de un Personal a secas, no sabríamos qué hacer: ¿le sumamos bonificación o le restamos descuento? No hay respuesta. Por eso:

Clase abstracta

Personal guarda los seis datos comunes, pero no se puede instanciar.

Método abstracto

getTipoPersonal() obliga a cada hija a declarar qué tipo es.

Interfaz

Calculable obliga a saber calcular el pago, cada uno a su manera.

La frase que resume el diseño: un Docente ES un Personal (por eso extends) y SABE calcular su pago (por eso implements).

2. Estructura del proyecto

Crea un paquete nuevo llamado formulariopersonal con cinco archivos.

Source Packages
      │
      └── formulariopersonal
      ├── Personal.java (clase abstracta: los datos comunes)
      ├── Calculable.java (interfaz: el contrato del pago)
      ├── Docente.java (extends + implements)
      ├── Administrativo.java (extends + implements)
      └── FormPersonal.java ← ejecuta este archivo (JFrame Form)
Archivo Qué es Para qué sirve
Personal.java Clase abstracta Guarda los seis datos comunes y obliga a declarar el tipo.
Calculable.java Interfaz Obliga a tener un método calcularPago().
Docente.java Clase hija Agrega bonificación. Suma al sueldo.
Administrativo.java Clase hija Agrega descuento. Resta al sueldo.
FormPersonal.java JFrame Form La ventana. Lee los datos y crea el objeto que corresponda.
Cómo crear el paquete: clic derecho en Source Packages → New → Java Package, escribe formulariopersonal y pulsa Finish.
Orden importante: crea los cuatro archivos de clases antes del formulario. Si creas primero el JFrame, NetBeans marcará en rojo los nombres Docente y Administrativo porque todavía no existen.

3. La clase abstracta Personal

Concepto que se demuestra: una clase abstracta reúne todo lo común y deja pendiente lo que cada hija debe decidir.

Clic derecho en el paquete → New → Java Class → nombre Personal.

Personal.java 
package formulariopersonal;

        // abstract = esta clase es solo un molde.
        // No se puede escribir new Personal(...) en ninguna parte.
        public abstract class Personal {

        // protected = visible aquí y en las clases hijas.
        protected String nombres;
        protected String apellidos;
        protected String dni;
        protected String direccion;
        protected String sexo;
        protected double sueldo;

        // Una clase abstracta SÍ tiene constructor.
        // No crea objetos Personal: lo usarán las hijas con super(...).
        public Personal(String nombres, String apellidos, String dni,
        String direccion, String sexo, double sueldo) {
        this.nombres = nombres;
        this.apellidos = apellidos;
        this.dni = dni;
        this.direccion = direccion;
        this.sexo = sexo;
        this.sueldo = sueldo;
        }

        // Método NORMAL: ya está resuelto y las dos hijas lo heredan igual.
        public void mostrarDatosGenerales() {
        System.out.println("Nombres: " + nombres);
        System.out.println("Apellidos: " + apellidos);
        System.out.println("DNI: " + dni);
        System.out.println("Dirección: " + direccion);
        System.out.println("Sexo: " + sexo);
        System.out.printf("Sueldo base: S/ %.2f%n", sueldo);
        }

        // Método ABSTRACTO: no tiene cuerpo, termina en punto y coma.
        // Cada hija está OBLIGADA a decir qué tipo de personal es.
        public abstract String getTipoPersonal();

        // Métodos get para que el formulario pueda leer los datos.
        public double getSueldo() {
        return sueldo;
        }

        public String getNombres() {
        return nombres;
        }
        }
Observa la mezcla: atributos, constructor, un método resuelto (mostrarDatosGenerales()) y un método pendiente (getTipoPersonal()). Esa combinación es exactamente lo que define a una clase abstracta.
Esto NO se puede hacer: Personal p = new Personal(...); produce el error Personal is abstract; cannot be instantiated. Y está bien que falle: un «personal genérico» no existe en la empresa.
Sobre this y super: dentro de este constructor usamos this.nombres = nombres porque el atributo y el parámetro se llaman igual; this señala al atributo del objeto. Más adelante, en Docente, usaremos super(...) para llamar a este constructor.

4. La interfaz Calculable

Concepto que se demuestra: la clase abstracta dice qué es el objeto; la interfaz dice qué sabe hacer.

En NetBeans: clic derecho en el paquete → New → Java Interface (no «Java Class»). Escribe Calculable y pulsa Finish.
Calculable.java 
package formulariopersonal;

        // Una interfaz es un contrato: una lista de compromisos.
        // No tiene atributos normales ni constructor.
        public interface Calculable {

        // Todo lo que sea "calculable" debe saber dar su pago final.
        // Sin cuerpo, termina en punto y coma.
        double calcularPago();
        }

Una sola línea, pero cambia el diseño por completo. Ahora cualquier clase que escriba implements Calculable queda obligada a tener un calcularPago().

4.1 Las dos frases que hay que memorizar

Docente ES un Personal → extends Personal
      Docente SABE calcular pago → implements Calculable
Aspecto extends Personal implements Calculable
Se usa con Una clase (o clase abstracta) Una interfaz
Responde a «¿qué soy?» «¿qué sé hacer?»
Cuántos se permiten Solo uno Varios, separados por coma
Qué recibe la clase Atributos y métodos ya escritos Solo la obligación de escribirlos
Aquí aporta Los seis datos y mostrarDatosGenerales() La obligación de calcularPago()
Orden obligatorio: primero extends, después implements. Escribir implements Calculable extends Personal es un error de compilación.

5. La clase Docente

Concepto que se demuestra: una hija hereda de la clase abstracta y a la vez cumple el contrato de la interfaz.

Docente.java 
package formulariopersonal;

        // extends Personal -> ES un personal (hereda los seis datos)
        // implements Calculable -> SABE calcular su pago
        public class Docente extends Personal implements Calculable {

        // Atributo propio de Docente. Administrativo no lo tiene.
        private double bonificacion;

        public Docente(String nombres, String apellidos, String dni,
        String direccion, String sexo, double sueldo,
        double bonificacion) {

        // super(...) llama al constructor de Personal.
        // SIEMPRE debe ser la primera instrucción.
        super(nombres, apellidos, dni, direccion, sexo, sueldo);

        this.bonificacion = bonificacion;
        }

        // Obligación que viene de la CLASE ABSTRACTA Personal.
        @Override
        public String getTipoPersonal() {
        return "Docente";
        }

        // Obligación que viene de la INTERFAZ Calculable.
        // Al docente se le SUMA la bonificación.
        @Override
        public double calcularPago() {
        return sueldo + bonificacion;
        }

        public double getBonificacion() {
        return bonificacion;
        }
        }
Fíjate en sueldo: dentro de calcularPago() usamos sueldo sin declararlo. Funciona porque es protected en Personal y esta clase es su hija. Si fuera private, tendríamos que usar getSueldo().

6. La clase Administrativo

Concepto que se demuestra: la misma obligación, resuelta con una fórmula distinta. Ese contraste es el polimorfismo.

Administrativo.java 
package formulariopersonal;

        public class Administrativo extends Personal implements Calculable {

        // Atributo propio de Administrativo.
        private double descuento;

        public Administrativo(String nombres, String apellidos, String dni,
        String direccion, String sexo, double sueldo,
        double descuento) {

        super(nombres, apellidos, dni, direccion, sexo, sueldo);

        this.descuento = descuento;
        }

        // Misma obligación que Docente, respuesta diferente.
        @Override
        public String getTipoPersonal() {
        return "Administrativo";
        }

        // Aquí se RESTA el descuento. Docente sumaba.
        @Override
        public double calcularPago() {
        return sueldo - descuento;
        }

        public double getDescuento() {
        return descuento;
        }
        }
Compara las dos clases: tienen la misma estructura y los mismos dos métodos obligatorios. Solo cambian el texto que devuelve getTipoPersonal() y el signo de la fórmula. Mismo contrato, distinta implementación.
El objetivo no es la planilla: las fórmulas son sueldo + bonificación y sueldo - descuento a propósito. Lo que importa es que sean diferentes, no que sean realistas.

8.4 Agrupar los RadioButton con ButtonGroup

Sin agrupar, los dos RadioButton se pueden marcar a la vez. El ButtonGroup garantiza que solo uno esté seleccionado.

  1. En Palette, busca Button Group (está en la sección Swing Controls, al final).
  2. Arrástralo sobre el formulario. No verás nada dibujado: es un componente invisible. Aparecerá en la ventana Navigator, abajo a la izquierda, dentro de Other Components.
  3. Selecciona rbMasculino en el formulario.
  4. En Properties, busca la propiedad buttonGroup y elige buttonGroup1 en la lista.
  5. Repite el paso anterior con rbFemenino, eligiendo el mismo buttonGroup1.
  6. Opcional: selecciona rbMasculino y marca su propiedad selected para que arranque elegido por defecto.
Compruébalo ahora: ejecuta el formulario con Shift + F6 y haz clic en los dos RadioButton. Si puedes marcar los dos al mismo tiempo, el ButtonGroup no está bien asignado: revisa que ambos apunten a buttonGroup1.

9. El campo adicional y la referencia polimórfica

9.1 Un solo campo para dos significados

Para no llenar el formulario de cajas, usamos un único campo txtAdicional que cambia de significado según el tipo elegido:

Si el combo muestra txtAdicional significa La fórmula será
Docente Bonificación sueldo + adicional
Administrativo Descuento sueldo - adicional

9.2 Cambiar la etiqueta automáticamente

Para que el usuario sepa qué está escribiendo, haremos que lblAdicional cambie de texto al cambiar el combo. Son tres líneas.

  1. En la vista Design, haz clic derecho sobre cbTipoPersonal.
  2. Elige Events → Action → actionPerformed.
  3. NetBeans salta a Source y crea el método cbTipoPersonalActionPerformed. Escribe dentro:
// Leemos la opción elegida en el combo.
        String tipo = cbTipoPersonal.getSelectedItem().toString();

        if (tipo.equals("Docente")) {
        lblAdicional.setText("Bonificación:");
        } else {
        lblAdicional.setText("Descuento:");
        }
Si algo sale mal: no borres a mano el método que NetBeans generó. Para quitar un evento, vuelve a Design, clic derecho en el componente → Events y desmarca el evento. NetBeans limpia el código por ti.

9.3 Declarar la referencia polimórfica

Esta es la línea más importante de toda la práctica.

  1. Cambia a la vista Source de FormPersonal.java.
  2. Busca la línea public class FormPersonal extends javax.swing.JFrame {.
  3. Justo debajo de esa llave de apertura y antes del constructor public FormPersonal(), escribe la declaración.
  4. No la escribas dentro de FormPersonal(), ni dentro de initComponents(), ni dentro de un evento de botón.
public class FormPersonal extends javax.swing.JFrame {

        // ---- LA LÍNEA CLAVE DE LA PRÁCTICA ----
        // El tipo es Personal (la clase abstracta),
        // pero guardará un Docente o un Administrativo.
        private Personal personal;

        public FormPersonal() {
        initComponents();
        }

        // ... aquí sigue el código que genera NetBeans ...
        }
 Personal personal ← una sola variable
      │
      ┌───────┴───────┐
      ▼ ▼
      Docente Administrativo ← dos objetos posibles
Por qué esto es polimorfismo: una única variable de tipo Personal puede referirse a objetos de dos clases distintas. Cuando más adelante llamemos a personal.getTipoPersonal(), Java decidirá durante la ejecución si ejecuta la versión de Docente o la de Administrativo, según el objeto que se haya creado.
¿Por qué está fuera de los métodos? Porque debe seguir existiendo cuando el evento termine. Si la declararas dentro de btnRegistrarActionPerformed, el objeto se perdería al salir del método y los otros botones no podrían usarlo.
Aviso de NetBeans: mientras no uses la variable, aparecerá un subrayado gris con el mensaje «field personal is never used». Es solo un aviso, no un error. Desaparecerá en el paso siguiente.

10. Programar el botón Registrar

Aquí se junta todo: leemos el formulario, creamos el objeto que corresponda y usamos la interfaz.

  1. Vuelve a la vista Design.
  2. Haz doble clic sobre el botón btnRegistrar.
  3. NetBeans crea y abre el método btnRegistrarActionPerformed.
  4. Escribe dentro el código de los tres pasos siguientes, uno tras otro.

10.1 Paso 1: leer los datos del formulario

// --- Datos de texto: se leen con getText() ---
        String nombres = txtNombres.getText();
        String apellidos = txtApellidos.getText();
        String dni = txtDni.getText();
        String direccion = txtDireccion.getText();

        // --- Sexo: se decide con el RadioButton marcado ---
        // isSelected() devuelve true si ese botón está elegido.
        String sexo;

        if (rbMasculino.isSelected()) {
        sexo = "Masculino";
        } else {
        sexo = "Femenino";
        }

        // --- Números: el formulario da texto, hay que convertirlo ---
        // Double.parseDouble transforma "2800" en el número 2800.0
        double sueldo = Double.parseDouble(txtSueldo.getText());
        double adicional = Double.parseDouble(txtAdicional.getText());

        // --- Tipo elegido en el combo ---
        String tipo = cbTipoPersonal.getSelectedItem().toString();
Por qué hay que convertir: un JTextField siempre entrega un String, aunque escribas números. Double.parseDouble() hace la traducción a double. Si el campo está vacío o tiene letras, el programa lanzará un error; lo veremos en la sección de errores comunes.

10.2 Paso 2: crear el objeto que corresponda

Este if es el corazón del polimorfismo: dos objetos distintos, una sola variable.

if (tipo.equals("Docente")) {

        // El valor adicional se interpreta como BONIFICACIÓN.
        personal = new Docente(nombres, apellidos, dni,
        direccion, sexo, sueldo, adicional);

        } else {

        // El valor adicional se interpreta como DESCUENTO.
        personal = new Administrativo(nombres, apellidos, dni,
        direccion, sexo, sueldo, adicional);
        }
Lee otra vez las dos asignaciones: a la izquierda siempre está la misma variable personal, de tipo Personal. A la derecha, dos clases diferentes. Eso es polimorfismo en una línea: la referencia del padre apunta al objeto de la hija.
Sobre equals: para comparar textos en Java se usa tipo.equals("Docente"), nunca tipo == "Docente". El == compara posiciones de memoria, no el contenido de las palabras.

10.3 Paso 3: usar la interfaz y mostrar en consola

Ahora necesitamos el pago final, que es el método de la interfaz Calculable.

// La forma más simple: llamamos al método sobre el objeto.
        // Java ejecuta la versión de Docente o de Administrativo
        // según lo que se haya creado arriba.
        double pagoFinal = ((Calculable) personal).calcularPago();

        // --- Salida en consola ---
        System.out.println("=================================");
        System.out.println(" DATOS DEL PERSONAL");
        System.out.println("=================================");

        // Método ABSTRACTO: cada hija devuelve su propio texto.
        System.out.println("Tipo: " + personal.getTipoPersonal());

        // Método NORMAL heredado de la clase abstracta.
        personal.mostrarDatosGenerales();

        // La etiqueta cambia según el tipo, igual que el formulario.
        if (tipo.equals("Docente")) {
        System.out.printf("Bonificación: S/ %.2f%n", adicional);
        } else {
        System.out.printf("Descuento: S/ %.2f%n", adicional);
        }

        System.out.printf("Pago final: S/ %.2f%n", pagoFinal);
        System.out.println("=================================");

10.4 Cómo evitar ese casting

La línea ((Calculable) personal).calcularPago() funciona, pero el paréntesis doble es incómodo y a un principiante no le dice nada. El casting hace falta porque la variable es de tipo Personal, y Personal no sabe nada de calcularPago().

Hay una salida mucho más clara: declarar una segunda variable del tipo de la interfaz.

  1. Vuelve al inicio de la clase, donde declaraste private Personal personal;.
  2. Añade debajo una segunda declaración.
private Personal personal; // lo que el objeto ES
        private Calculable calculable; // lo que el objeto SABE hacer

Y en el if del paso 2, guarda el objeto en las dos variables a la vez:

if (tipo.equals("Docente")) {

        Docente docente = new Docente(nombres, apellidos, dni,
        direccion, sexo, sueldo, adicional);

        personal = docente; // lo vemos como Personal
        calculable = docente; // y también como Calculable

        } else {

        Administrativo admin = new Administrativo(nombres, apellidos, dni,
        direccion, sexo, sueldo, adicional);

        personal = admin;
        calculable = admin;
        }

        // Ahora la llamada se lee de corrido, sin casting:
        double pagoFinal = calculable.calcularPago();
Lo que esto enseña: existe un solo objeto en memoria. Las dos variables apuntan a él, pero cada una lo ve de una manera: personal ve los datos y el tipo; calculable ve el pago. Es la diferencia entre «qué es» y «qué sabe hacer», ahora en código ejecutable.
Compruébalo: escribe calculable.getTipoPersonal() y NetBeans lo marcará en rojo, aunque el objeto real sí tiene ese método. La variable limita lo que puedes llamar. Bórralo después de comprobarlo.
Usa una de las dos versiones, no las dos. Si eliges la de 10.4, borra la línea con ((Calculable) personal) del paso 3 y deja solo double pagoFinal = calculable.calcularPago();.

11. Botones Limpiar y Salir

11.1 Botón Limpiar

En Design, doble clic sobre btnLimpiar y escribe:

// Vaciamos todas las cajas de texto.
        txtNombres.setText("");
        txtApellidos.setText("");
        txtDni.setText("");
        txtDireccion.setText("");
        txtSueldo.setText("");
        txtAdicional.setText("");

        // Volvemos a la primera opción del combo (Docente).
        cbTipoPersonal.setSelectedIndex(0);

        // Y devolvemos la etiqueta a "Bonificación:".
        lblAdicional.setText("Bonificación:");

        // Dejamos marcado Masculino.
        rbMasculino.setSelected(true);

        // El cursor regresa al primer campo.
        txtNombres.requestFocus();
requestFocus(): coloca el cursor parpadeando dentro de txtNombres, para que el usuario pueda escribir de inmediato sin tener que hacer clic.
Si no agregaste la etiqueta dinámica de la sección 9.2, borra la línea lblAdicional.setText("Bonificación:");, porque esa etiqueta no tendrá ese nombre de variable y el código no compilará.

11.2 Botón Salir

Doble clic sobre btnSalir y escribe una sola línea:

System.exit(0);
System.exit(0) frente a dispose(): exit(0) termina todo el programa; el 0 significa «cerró sin errores». dispose() solo cierra esta ventana y dejaría el programa vivo si hubiera otras abiertas.

13. ¿Dónde está cada concepto?

Esta sección es la más importante para el examen. Cada concepto del curso, señalado en el código que acabas de escribir.

Herencia

public class Docente extends Personal

Docente recibe los seis atributos y mostrarDatosGenerales() sin volver a escribirlos. Archivos: Docente.java y Administrativo.java.

Clase abstracta

public abstract class Personal

Plantilla común que no se puede instanciar. Evita crear un «personal genérico» que no existe en la empresa. Archivo: Personal.java.

Método abstracto

public abstract String getTipoPersonal();

Sin cuerpo, termina en punto y coma. Obliga a las dos hijas a declarar qué tipo de personal son. Archivo: Personal.java.

Interfaz

public interface Calculable {
          double calcularPago();
          }

Un contrato de capacidades. No dice qué es el objeto, dice qué sabe hacer. Archivo: Calculable.java.

Implementación de la interfaz

public class Docente extends Personal implements Calculable

Al firmar el contrato, la clase queda obligada a escribir calcularPago(). Primero extends, después implements.

Polimorfismo

private Personal personal;

          personal = new Docente(...); // o bien
          personal = new Administrativo(...);

Una sola variable del tipo padre guarda objetos de dos clases distintas. Al llamar a getTipoPersonal(), Java elige la versión correcta en tiempo de ejecución. Archivo: FormPersonal.java.

Sobrescritura

@Override
          public double calcularPago() {
          return sueldo + bonificacion;
          }

Cada hija escribe su propia versión del método obligatorio. Docente suma, Administrativo resta.

Constructor del padre

super(nombres, apellidos, dni, direccion, sexo, sueldo);

Llama al constructor de Personal para inicializar los seis datos heredados. Debe ser la primera instrucción del constructor de la hija.

Encapsulamiento

protected double sueldo; // visible en las hijas
          private double bonificacion; // solo dentro de Docente

protected permite a Docente usar sueldo directamente; private protege lo que es exclusivo de cada hija.

16. Resumen

Los cinco archivos y el concepto que aporta cada uno:

Archivo Palabra clave Concepto que demuestra
Personal.java abstract class Clase abstracta y método abstracto
Calculable.java interface Contrato de capacidades
Docente.java extends + implements Herencia, super, @Override
Administrativo.java extends + implements La misma obligación, otra fórmula
FormPersonal.java Personal personal; Polimorfismo en tiempo de ejecución
El recorrido completo del curso: clase normal → herencia con extends → sobrescritura con @Override → polimorfismo → clase abstracta con abstract → interfaz con implements → esta práctica, donde todo funciona junto.
La pregunta que decide el diseño: ¿la relación es «es un»? Usa extends. ¿Es «sabe hacer»? Usa implements. Aquí eran las dos: un Docente es personal y sabe calcular su pago.
