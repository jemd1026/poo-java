¿Por qué SQL sigue vigente? Evolución y futuro de las bases de datos relacionales

Lectura de divulgación académica adaptada para Programación Orientada a Objetos · Sesiones 11 y 12
Fuente científica principal: Michael Stonebraker y Andrew Pavlo (2024), What Goes Around Comes Around... And Around..., SIGMOD Record, 53(2). Esta lectura es una síntesis pedagógica original, no una traducción literal. Los ejemplos de Java y MARKET_DB son aplicaciones didácticas añadidas.

1. Una tecnología que ha resistido el paso del tiempo

En informática es frecuente que una tecnología prometedora anuncie el reemplazo de otra. Sin embargo, algunas ideas sobreviven porque resuelven problemas fundamentales. El modelo relacional y SQL son ejemplos de esta permanencia. En su artículo de 2024, Stonebraker y Pavlo revisan varias décadas de innovaciones en sistemas de bases de datos y sostienen que las alternativas no han desplazado de manera general al modelo relacional. Por el contrario, muchos sistemas nuevos han terminado incorporando características de SQL.

El modelo relacional organiza los datos en relaciones, que en la práctica se representan habitualmente mediante tablas. Una tabla de clientes contiene información de compradores; otra de productos describe artículos disponibles; una de ventas registra transacciones. Los identificadores permiten asociar esos registros sin repetir innecesariamente todos los datos. Esta organización resulta especialmente útil cuando una aplicación debe mantener información consistente.

SQL, sigla de Structured Query Language (lenguaje de consulta estructurado), permite definir estructuras, insertar y modificar datos, y recuperar información mediante consultas. En un minimarket, una consulta puede mostrar las ventas de un día o los productos con poco stock. No es necesario programar manualmente cada paso interno de búsqueda: el gestor de base de datos interpreta y optimiza la instrucción.

Los autores recuerdan que antes y después del modelo relacional surgieron enfoques jerárquicos, de red, orientados a objetos y semiestructurados. Cada uno buscó atender necesidades concretas. La historia de las bases de datos no consiste, por tanto, en una sola tecnología perfecta, sino en sucesivos intentos por equilibrar flexibilidad, rendimiento, facilidad de uso y confiabilidad.

Una enseñanza importante del artículo es que la permanencia de SQL no significa inmovilidad. Sus implementaciones y extensiones han cambiado para responder a nuevos tipos de datos y aplicaciones. Así, aprender SQL proporciona una base conceptual que sigue siendo útil incluso cuando aparecen plataformas distintas.

2. El desafío de NoSQL y la importancia de las relaciones

Con el crecimiento de internet aparecieron aplicaciones que necesitaban almacenar cantidades enormes de información y responder a millones de solicitudes. En ese contexto ganaron popularidad sistemas llamados NoSQL, entre ellos las bases de documentos y los almacenes clave-valor. Algunas soluciones priorizaron la flexibilidad del formato o el acceso rápido a datos específicos, aunque a veces ofrecían menos herramientas para consultas complejas o transacciones.

Una base de documentos puede guardar la información de un cliente junto con una lista de compras en una estructura semejante a JSON. Este diseño puede ser cómodo para ciertos usos. Sin embargo, cuando varias operaciones comparten productos, clientes y registros de venta, mantener la consistencia exige decisiones cuidadosas. Los datos repetidos pueden requerir múltiples actualizaciones y las relaciones entre entidades siguen existiendo aunque no se representen mediante claves foráneas.

Stonebraker y Pavlo destacan un hecho llamativo: diversos sistemas que inicialmente se presentaron como alternativas a SQL incorporaron después lenguajes de consulta similares a SQL y mejores mecanismos de transacciones. Para los autores, esta convergencia muestra que las necesidades resueltas por los sistemas relacionales continúan siendo relevantes. No significa que NoSQL carezca de utilidad, sino que sus ventajas dependen del problema que se desea resolver.

Ejemplo: un minimarket con ventas relacionadas

Imaginemos una base de datos MARKET_DB con tablas clientes, productos, ventas y detalle_ventas. Cada venta pertenece a un cliente y puede incluir varios productos. El detalle almacena cantidades y precios correspondientes a cada transacción. De esta forma, el sistema puede responder quién compró, qué compró y cuánto pagó.

Las claves primarias identifican registros de manera única. Las claves foráneas expresan las relaciones entre tablas. Si se intenta registrar un detalle para una venta inexistente, las restricciones de integridad pueden impedir que se guarde un dato incoherente. Esta capacidad es importante en operaciones comerciales donde la información debe mantenerse correcta.

El artículo científico no propone un modelo concreto de minimarket: este ejemplo permite trasladar sus ideas al trabajo de clase. La decisión entre SQL y NoSQL no debe depender de una moda, sino de los requisitos de cada aplicación: tipo de consultas, volumen de información, consistencia y facilidad de mantenimiento.

3. Nube, grandes datos e inteligencia artificial

La evolución de las bases de datos no se limita a la forma de organizar la información. También ha cambiado la arquitectura de los sistemas. El artículo analiza tecnologías de almacenamiento por columnas, bases de datos en la nube, plataformas de análisis y sistemas que aprovechan hardware especializado. Estas innovaciones responden a nuevas exigencias de rendimiento y escalabilidad.

Un negocio pequeño puede consultar las ventas del día; una cadena de tiendas necesita analizar millones de transacciones históricas. Para este segundo escenario, las bases orientadas al análisis pueden organizar físicamente los datos por columnas, lo que favorece ciertas operaciones de agregación. Los autores explican que las empresas han utilizado datos históricos de ventas para mejorar decisiones relacionadas con el inventario y la reposición de productos.

La nube añade otra dimensión: los recursos informáticos pueden contratarse y ajustarse según las necesidades. En vez de depender únicamente de un servidor físico propio, una organización puede utilizar servicios administrados. Esto no elimina la necesidad de comprender las tablas, las consultas y la integridad de los datos. Cambia el lugar y la manera en que se ejecutan y administran los sistemas.

La inteligencia artificial también impulsa nuevas formas de búsqueda. Las bases de datos vectoriales almacenan representaciones numéricas de textos, imágenes u otros contenidos y permiten buscar elementos semejantes. Por ejemplo, una aplicación podría encontrar descripciones de productos similares aunque no contengan exactamente las mismas palabras. Stonebraker y Pavlo observan que los gestores relacionales han comenzado a incorporar capacidades de búsqueda vectorial, lo que refuerza su argumento sobre la adaptación de SQL.

Conviene distinguir dos tipos de preguntas. Una consulta relacional tradicional podría recuperar todas las ventas de un cliente durante un mes. Una búsqueda por similitud podría identificar productos cuya descripción se parece a la de un artículo solicitado. No son operaciones idénticas, pero pueden coexistir en sistemas modernos.

Los autores son críticos con la idea de que cada nueva tendencia necesite reemplazar completamente las bases de datos existentes. Su posición es que las tecnologías relacionales pueden integrar muchas funciones nuevas, aunque reconocen que algunos sistemas especializados conservan ventajas en aplicaciones particulares. Esta perspectiva invita a evaluar la evidencia técnica antes de adoptar una plataforma.

4. ¿Qué significa esto para un estudiante que programa en Java?

El artículo de Stonebraker y Pavlo estudia principalmente la evolución de los sistemas de bases de datos; no es un tutorial de Java ni de JDBC. Sin embargo, sus conclusiones permiten comprender por qué aprender a trabajar con bases relacionales sigue siendo importante para quienes desarrollan aplicaciones.

En el laboratorio, los estudiantes diseñan MARKET_DB con SQL Server 2022 o 2025. En la sesión de diseño crean tablas, establecen relaciones y practican sentencias SQL. Después, desde Java, utilizan JDBC (Java Database Connectivity) para establecer una conexión y enviar consultas a la base de datos. Así se relacionan dos aprendizajes: la organización persistente de la información y el comportamiento de un programa orientado a objetos.

Supongamos que un empleado registra una venta. La aplicación necesita identificar al cliente, seleccionar los productos, calcular el total y guardar la operación. Las clases Java pueden distribuir responsabilidades, mientras SQL Server almacena la información. Un controlador puede coordinar el proceso y una clase de acceso a datos puede ejecutar las instrucciones SQL. La conexión JDBC es el medio de comunicación entre ambos componentes.

Este ejemplo también permite apreciar la importancia de las transacciones. Una venta puede requerir registrar su cabecera, sus detalles y actualizar el stock. Si ocurre un error a mitad del proceso, no sería deseable conservar una venta incompleta. Las transacciones permiten tratar un conjunto de cambios como una unidad de trabajo, de manera que se confirmen o se reviertan según corresponda.

Otro aprendizaje es que conocer SQL no obliga a utilizar exclusivamente un único gestor. La sintaxis concreta y las funciones pueden variar, pero las ideas de relaciones, consultas, integridad y transacciones se aplican en diferentes sistemas. Por eso SQL Server sirve como un entorno práctico para adquirir competencias transferibles.

5. Reflexión final

El argumento central del artículo es que SQL y el modelo relacional han demostrado una notable capacidad de adaptación. La aparición de NoSQL, la nube y las bases vectoriales no ha producido su desaparición. En muchos casos, las nuevas tecnologías incorporan ideas relacionales, mientras los gestores tradicionales añaden funciones antes consideradas especializadas.

Para un futuro profesional, la pregunta no debería ser solamente «¿qué tecnología es la más nueva?», sino «¿qué tecnología responde mejor a los requisitos del sistema?». Comprender SQL y sus fundamentos ayuda a tomar decisiones fundamentadas y a diseñar aplicaciones confiables, sin dejar de explorar herramientas emergentes.
