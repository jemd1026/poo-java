Relaciones entre clases y patrones

Las clases no trabajan aisladas. Se relacionan para colaborar y los patrones de diseño nos ayudan a organizar esas colaboraciones.

Ruta de aprendizaje: primero observamos cómo se relacionan las clases; después entendemos cómo un patrón propone una solución reutilizable a un problema frecuente.

1. ¿Cómo se relacionan las clases?

En UML, una relación muestra que dos clases tienen algún vínculo. La relación no siempre significa que una clase “contenga” a la otra: puede significar que colaboran, que una está formada por otra o que existe una relación de herencia.

Asociación

Dos clases colaboran de forma general.

Agregación

Un objeto agrupa a otros, pero pueden vivir por separado.

Composición

Un objeto está formado por otros que dependen de su ciclo de vida.

UML en una frase: los rectángulos representan clases y las líneas muestran cómo se conectan.

2. Asociación: “colabora con”

Usaremos siempre el ejemplo de una biblioteca. En esta primera relación, un Bibliotecario utiliza un Libro para registrarlo. Ninguna clase es dueña de la otra.

Ejemplo UML · el bibliotecario registra un libro

BibliotecarionombreregistrarLibro()
registra
LibrotitulomostrarDatos()
asociación

Código Java ejecutable · EjemploAsociacion.java

public class EjemploAsociacion {

    static class Libro {
        String titulo;

        Libro(String titulo) {
            this.titulo = titulo;
        }

        void mostrarDatos() {
            System.out.println("Libro: " + titulo);
        }
    }

    static class Bibliotecario {
        // Recibe un Libro solo para utilizarlo.
        void registrarLibro(Libro libro) {
            libro.mostrarDatos();
        }
    }

    public static void main(String[] args) {
        Libro libro = new Libro("Java desde cero");
        Bibliotecario bibliotecario = new Bibliotecario();

        // El bibliotecario colabora con el libro.
        bibliotecario.registrarLibro(libro);
    }
}

Resultado esperado

Libro: Java desde cero
Diferencia inicial: aquí solo existe colaboración. El Bibliotecario usa al Libro, pero no lo contiene ni depende de su creación.

3. Agregación: “tiene” pero no es dueño total

Ahora la Biblioteca agrupa varios Libro. Los libros pueden existir antes de la biblioteca y también podrían formar parte de otra biblioteca.

Ejemplo UML · una biblioteca tiene libros

BibliotecanombremostrarLibro()
tiene
LibrotitulomostrarDatos()
agregación

Código Java ejecutable · EjemploAgregacion.java

public class EjemploAgregacion {

    static class Libro {
        String titulo;

        Libro(String titulo) {
            this.titulo = titulo;
        }
    }

    static class Biblioteca {
        // La biblioteca recibe un libro creado fuera de ella.
        private Libro libro;

        // Constructor: recibe un Libro que ya existe.
        Biblioteca(Libro libro) {
            // Guarda la referencia al libro en la biblioteca.
            this.libro = libro;
        }

        void mostrarLibro() {
            System.out.println("Libro en biblioteca: " + libro.titulo);
        }
    }

    public static void main(String[] args) {
        // El libro puede existir antes que la biblioteca.
        Libro libro = new Libro("Java desde cero");
        Biblioteca biblioteca = new Biblioteca(libro);

        biblioteca.mostrarLibro();
    }
}

Resultado esperado

Libro en biblioteca: Java desde cero
Diferencia con asociación: antes el Bibliotecario solo usaba al Libro; ahora la Biblioteca mantiene una referencia al libro como parte de su grupo.
Pero sigue siendo independiente: el Libro se creó fuera de la Biblioteca, por eso puede existir aunque la biblioteca desaparezca.

4. Composición: “forma parte de”

El mismo ejemplo de biblioteca nos muestra una relación fuerte: un Libro crea sus propios Capitulo. El capítulo forma parte del libro y depende de él.

Ejemplo UML · un libro está formado por capítulos

LibrotitulomostrarCapitulo()
contiene
Capitulonumeroleer()
composición

Código Java ejecutable · EjemploComposicion.java

public class EjemploComposicion {

    static class Capitulo {
        void leer() {
            System.out.println("Leyendo capítulo del libro");
        }
    }

    static class Libro {
        private Capitulo capitulo;

        Libro() {
            // El Libro crea su propio Capitulo.
            capitulo = new Capitulo();
        }

        void mostrarCapitulo() {
            capitulo.leer();
        }
    }

    public static void main(String[] args) {
        Libro libro = new Libro();

        // El capítulo nace como parte del libro.
        libro.mostrarCapitulo();
    }
}

Resultado esperado

Leyendo capítulo del libro
Diferencia con agregación: en la agregación, el libro se creó fuera de la biblioteca; en la composición, el capítulo se crea dentro del libro y depende de él.
Regla sencilla: si el Libro deja de existir, sus Capitulo ya no tienen sentido como parte de ese libro.

5. Herencia: “es un”

Continuamos con la biblioteca. Un LibroDigital es un tipo especial de Libro; por eso puede heredar sus datos y métodos.

Ejemplo UML · un libro digital es un libro

LibrotitulomostrarDatos()
extends
LibroDigitalformatodescargar()

Código Java ejecutable · EjemploHerencia.java

public class EjemploHerencia {

    static class Libro {
        void mostrarDatos() {
            System.out.println("Libro de programación");
        }
    }

    // LibroDigital es un tipo especializado de Libro.
    static class LibroDigital extends Libro {
        void descargar() {
            System.out.println("Descargando libro digital");
        }
    }

    public static void main(String[] args) {
        LibroDigital libro = new LibroDigital();

        // Método heredado de Libro.
        libro.mostrarDatos();
        // Método propio de LibroDigital.
        libro.descargar();
    }
}

Resultado esperado

Libro de programación
Descargando libro digital
Diferencia con composición: Capitulo forma parte de un Libro; en cambio, LibroDigital es un Libro especializado y hereda sus características.

6. ¿Qué es un patrón de diseño?

Un patrón de diseño es una solución conocida, reutilizable y adaptable para un problema que aparece con frecuencia al diseñar software.

No es una copia de código: es una idea de organización. El código final se adapta al problema, a los nombres y a las reglas de cada programa.
Problemaaparece varias veces
→
Patrónpropone una estructura
→
Soluciónse adapta al proyecto

Clasificación de patrones

Creacionales

Ayudan a crear objetos sin depender demasiado de clases concretas. Ejemplo: Factory.

Estructurales

Organizan clases y objetos para formar estructuras más grandes. Ejemplo: Adapter.

De comportamiento

Organizan la comunicación y las responsabilidades. Ejemplo: Observer.

¿Qué problema ayudan a resolver? Dependencias directas entre clases, dificultad para cambiar tipos de objetos, creación compleja y comunicación rígida entre objetos.

7. Ejemplo básico: patrón Factory

Seguimos con la biblioteca. Una fábrica decide si debe crear un LibroDigital o un LibroFisico. El programa principal solo solicita un Libro.

Ejemplo UML simplificado

LibroFactorycrear(tipo)
crea
Libroabrir()
centraliza la creación

Código Java ejecutable · EjemploFactory.java

public class EjemploFactory {

    static class Libro {
        void abrir() {
            System.out.println("Abriendo libro");
        }
    }

    static class LibroDigital extends Libro {
        void abrir() {
            System.out.println("Abriendo libro digital");
        }
    }

    static class LibroFisico extends Libro {
        void abrir() {
            System.out.println("Abriendo libro físico");
        }
    }

    static class LibroFactory {
        static Libro crear(String tipo) {
            // La fábrica decide qué clase concreta crear.
            if (tipo.equals("digital")) {
                return new LibroDigital();
            }
            return new LibroFisico();
        }
    }

    public static void main(String[] args) {
        // El programa solicita un Libro, sin usar new directamente.
        Libro libro = LibroFactory.crear("digital");
        libro.abrir();
    }
}

Resultado esperado

Abriendo libro digital
Diferencia con las relaciones anteriores: Factory no describe si un objeto contiene o hereda de otro; organiza el proceso de creación para que el programa principal dependa de Libro y no de una clase concreta.

8. Ocho ejercicios para practicar

Resuelve los ejercicios en orden. Los cuatro primeros usan la biblioteca para que puedas concentrarte en distinguir las relaciones; los siguientes aplican lo aprendido en otros contextos.

Entrega mínima para cada ejercicio:
  1. Dibuja las clases como rectángulos UML con atributos y métodos.
  2. Representa la relación con el símbolo correcto.
  3. Escribe las clases Java con constructor, atributos y métodos básicos.
  4. Crea una clase PruebaEjercicioN con main para crear objetos y mostrar un resultado.

Ejercicio 1 · Autor y libro

Un autor puede escribir uno o varios libros. El autor y el libro pueden existir de forma independiente.

Autor 1 ── escribe ── 0..* Libro
  • Relación: asociación.
  • Autor: nombre, nacionalidad; escribirLibro().
  • Libro: titulo, isbn; mostrarDatos().

Archivos sugeridos: Autor.java, Libro.java, PruebaEjercicio1.java.

Ejercicio 2 · Biblioteca y libros

Una biblioteca agrupa libros. Un libro puede existir antes de registrarse y puede cambiar de biblioteca.

Biblioteca ◇── 0..* Libro
  • Relación: agregación.
  • Biblioteca: nombre, libro; agregarLibro(), mostrarLibros().
  • Libro: titulo, autor; mostrarDatos().

Archivos sugeridos: Biblioteca.java, Libro.java, PruebaEjercicio2.java.

Ejercicio 3 · Libro y capítulos

Un libro crea sus capítulos. Los capítulos pertenecen al libro y no se manejan fuera de él.

Libro ◆── 1..* Capitulo
  • Relación: composición.
  • Libro: titulo, capitulo; agregarCapitulo(), mostrarContenido().
  • Capitulo: numero, titulo; leer().

Archivos sugeridos: Libro.java, Capitulo.java, PruebaEjercicio3.java.

Ejercicio 4 · Libro digital

Un libro digital es un tipo especializado de libro y agrega la posibilidad de descargarse.

LibroDigital ─▷ Libro
  • Relación: herencia con extends.
  • Libro: titulo, autor; mostrarDatos().
  • LibroDigital: formato; descargar().

Archivos sugeridos: Libro.java, LibroDigital.java, PruebaEjercicio4.java.

Ejercicio 5 · Fábrica de libros

Una fábrica debe crear un libro físico o digital según el texto recibido.

LibroFactory ── crea ──> Libro
  • Patrón: Factory.
  • Libro: titulo; abrir().
  • LibroFisico y LibroDigital: redefinen abrir().
  • LibroFactory: crear(tipo).

Archivos sugeridos: Libro.java, LibroFisico.java, LibroDigital.java, LibroFactory.java, PruebaEjercicio5.java.

Ejercicio 6 · Cliente y producto

Un cliente consulta un producto y puede agregarlo a una compra. Ninguno depende del ciclo de vida del otro.

Cliente ── consulta ──> Producto
  • Relación: asociación.
  • Cliente: nombre, dni; consultarProducto().
  • Producto: codigo, precio; mostrarPrecio().

Archivos sugeridos: Cliente.java, Producto.java, PruebaEjercicio6.java.

Ejercicio 7 · Curso y estudiantes

Un curso agrupa estudiantes inscritos. Un estudiante puede retirarse y continuar existiendo.

Curso ◇── 0..* Estudiante
  • Relación: agregación.
  • Curso: nombre, codigo; inscribir(), listarEstudiantes().
  • Estudiante: nombre, registro; mostrarDatos().

Archivos sugeridos: Curso.java, Estudiante.java, PruebaEjercicio7.java.

Ejercicio 8 · Pedido y detalles

Un pedido se compone de detalles y un pedido express es un tipo de pedido con una tarifa adicional.

Pedido ◆── DetallePedido
PedidoExpress ─▷ Pedido
  • Relaciones: composición y herencia.
  • Pedido: numero; agregarDetalle(), calcularTotal().
  • DetallePedido: producto, cantidad; calcularSubtotal().
  • PedidoExpress: tarifa; calcularTotal().

Archivos sugeridos: Pedido.java, DetallePedido.java, PedidoExpress.java, PruebaEjercicio8.java.

Consejo: antes de escribir Java, responde: ¿las clases solo colaboran?, ¿una agrupa a la otra?, ¿la parte depende del todo?, ¿o realmente es un tipo especializado? Esa respuesta determina el símbolo UML y la estructura del código.
