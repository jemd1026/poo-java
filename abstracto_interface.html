Clases abstractas e interfaces en Java

Continuación directa de la guía de herencia y polimorfismo. Seguiremos usando Persona, Empleado y Consultor para descubrir por qué necesitamos abstract e interface, y cuándo conviene usar cada uno.

1. ¿Qué problema aparece?

En la guía anterior escribimos una clase Persona con un método actividad(). Después Empleado y Consultor lo sobrescribieron con @Override. Todo funcionó bien, pero quedaron dos detalles incómodos.

1.1 Primer problema: objetos que no deberían existir

Nada nos impide escribir esta línea:

Persona persona = new Persona(1, "12345678", "Ana", "Rojas");
        persona.actividad();

Resultado en consola:

La persona realiza una actividad

¿Qué actividad realiza exactamente? Ninguna. Una persona genérica no trabaja ni asesora. Solo tiene sentido como plantilla común para Empleado y Consultor. En el mundo real no contratamos «personas genéricas»: contratamos empleados o consultores.

1.2 Segundo problema: mensajes de relleno

El método actividad() de Persona imprime un texto que nunca queremos ver. Es un relleno que existe solo para que las clases hijas tengan algo que sobrescribir.

Peor aún: si mañana creamos Estudiante extends Persona y olvidamos escribir @Override actividad(), el programa compila sin errores y muestra el mensaje de relleno. El error pasa desapercibido.

1.3 La solución

Java ofrece dos herramientas para resolver exactamente esto:

Clase abstracta

Una plantilla que no se puede instanciar y que puede obligar a las hijas a escribir ciertos métodos.

Interfaz

Un contrato de métodos que cualquier clase puede firmar, incluso varios contratos a la vez.

Objetivo

Que el compilador detecte los olvidos, en lugar de descubrirlos ejecutando el programa.

2. Clases abstractas desde cero

2.1 ¿Qué es una clase abstracta?

Una clase abstracta es una clase incompleta a propósito. Sirve como molde: define lo que todas sus hijas tienen en común, pero deja sin resolver aquello que cada hija debe decidir por su cuenta.

Comparación sencilla: un formulario en blanco es una clase abstracta. Tiene los campos definidos (nombre, DNI, dirección), pero no sirve de nada hasta que alguien lo llena. El formulario lleno es el objeto.

2.2 ¿Para qué sirve?

  • Compartir atributos y métodos ya escritos entre varias clases hijas.
  • Impedir que se creen objetos de la clase padre.
  • Obligar a las clases hijas a implementar determinados métodos.

2.3 La palabra reservada abstract

abstract se escribe antes de class para declarar una clase abstracta, o antes del tipo de retorno para declarar un método abstracto.

public abstract class Figura { // clase abstracta
        public abstract double area(); // método abstracto: sin cuerpo
        }

2.4 Clase normal frente a clase abstracta

Característica Clase normal Clase abstracta
Palabra reservada class abstract class
Se puede usar con new Sí No
Métodos sin cuerpo No los permite Sí, los métodos abstractos
Atributos y constructor Sí Sí
Se usa como padre Opcional Es su única razón de existir

2.5 ¿Por qué no se puede instanciar?

Porque puede tener métodos sin cuerpo. Si Java permitiera crear el objeto y alguien llamara a un método abstracto, no habría ninguna instrucción que ejecutar.

Figura f = new Figura(); // ERROR de compilación
        f.area(); // ¿qué código se ejecutaría aquí?
Error común: Figura is abstract; cannot be instantiated. NetBeans lo marca en rojo antes de ejecutar. No es un fallo del programa: es la protección funcionando.

2.6 ¿Qué es un método abstracto?

Es un método que declara solo su firma —nombre, parámetros y tipo de retorno— y termina en punto y coma, sin llaves. Es una obligación escrita: «toda hija debe tener este método».

Aspecto Método normal Método abstracto
Forma void saludar() { ... } abstract void saludar();
Tiene cuerpo Sí, entre llaves No, termina en ;
La hija lo sobrescribe Si quiere Está obligada
Dónde puede estar En cualquier clase Solo en clase abstracta o interfaz
Regla que se olvida mucho: una clase abstracta puede tener métodos normales y métodos abstractos mezclados. Lo que no puede existir es un método abstracto dentro de una clase normal.

2.7 Ejemplo mínimo completo y ejecutable

Concepto que se demuestra: una clase abstracta define lo común (el nombre de la figura) y deja abierto lo que cada hija calcula de forma distinta (el área).

Clases necesarias: crea el paquete figuras con cuatro archivos. Los tres primeros son las clases; el cuarto es el que ejecutarás.

Source Packages
│
└── figuras
    ├── Figura.java          (clase abstracta)
    ├── Cuadrado.java        (clase hija)
    ├── Circulo.java         (clase hija)
    └── PruebaFigura.java    ← ejecuta este archivo
Figura.java 
package figuras;

public abstract class Figura {
        protected String nombre;

        // Una clase abstracta SÍ puede tener constructor.
        // Lo usarán las clases hijas mediante super(...).
        public Figura(String nombre) {
        this.nombre = nombre;
        }

        // Método normal: ya está resuelto, todas lo heredan igual.
        public void mostrarNombre() {
        System.out.println("Figura: " + nombre);
        }

        // Método abstracto: cada figura calcula su área de forma distinta,
        // así que aquí NO se escribe el cuerpo.
        public abstract double area();
        }
Cuadrado.java 
package figuras;

        public class Cuadrado extends Figura {
        private double lado;

        public Cuadrado(double lado) {
        super("Cuadrado"); // llama al constructor de Figura
        this.lado = lado;
        }

        @Override // obligatorio: Figura.area() es abstracto
        public double area() {
        return lado * lado;
        }
        }
Circulo.java 
package figuras;

        public class Circulo extends Figura {
        private double radio;

        public Circulo(double radio) {
        super("Círculo");
        this.radio = radio;
        }

        @Override
        public double area() {
        return 3.1416 * radio * radio;
        }
        }

▶ Ejecutar el ejemplo

Las tres clases anteriores no hacen nada por sí solas: nadie las llama. Necesitamos una cuarta clase con main(). Ejecuta este archivo: PruebaFigura.java.

PruebaFigura.java ← ejecutar 
package figuras;

        public class PruebaFigura {

        public static void main(String[] args) {

        // Figura es abstracta: la línea siguiente NO compila.
        // Figura f = new Figura("Genérica");

        // Sí podemos crear las hijas, porque ellas ya implementan area().
        Cuadrado cuadrado = new Cuadrado(4);
        Circulo circulo = new Circulo(2);

        // mostrarNombre() es heredado; area() es la versión de cada hija.
        cuadrado.mostrarNombre();
        System.out.println("Área: " + cuadrado.area());

        System.out.println("------------------------");

        circulo.mostrarNombre();
        System.out.println("Área: " + circulo.area());

        System.out.println("------------------------");

        // Polimorfismo: una sola referencia de tipo Figura,
        // dos objetos distintos, dos áreas distintas.
        Figura[] figuras = { cuadrado, circulo };

        for (Figura figura : figuras) {
        // printf da formato: %s texto, %.2f número con 2 decimales, %n salto
        System.out.printf("%s tiene un área de %.2f%n",
        figura.nombre, figura.area());
        }
        }
        }

Qué ocurre: mostrarNombre() se ejecuta igual para las dos figuras porque está resuelto en Figura. En cambio area() cambia de resultado según el objeto: Java elige la versión de Cuadrado o de Circulo durante la ejecución. El bucle final usa el tipo abstracto como referencia y funciona con ambos.

💻 Resultado esperado en consola

Figura: Cuadrado
Área: 16.0
------------------------
Figura: Círculo
Área: 12.5664
------------------------
Cuadrado tiene un área de 16,00
Círculo tiene un área de 12,57
Sobre el separador decimal: printf usa la configuración regional del sistema. En Windows en español verás 16,00 con coma; en inglés, 16.00 con punto. println siempre muestra punto. No es un error.

2.8 extends y @Override en este contexto

Son las mismas palabras de la guía anterior, pero ahora cambian de significado:

Palabra Con herencia normal Con clase abstracta
extends Hereda código ya escrito. Hereda código y acepta obligaciones.
@Override Reemplaza un comportamiento existente. Completa un método que estaba vacío.
Idea clave: @Override no es obligatorio para que el programa funcione, pero escríbelo siempre. Si te equivocas en el nombre del método, el compilador te avisa de inmediato.

3. Convertir Persona en clase abstracta

Volvamos al ejemplo conocido. No cambiaremos el proyecto: solo tres detalles del código anterior.

3.1 Antes y después

Código anterior (guía de herencia):

public class Persona {

        public void actividad() {
        System.out.println("La persona realiza una actividad");
        }
        }

Código nuevo (clase abstracta):

public abstract class Persona {

        public abstract void actividad();
        }
Cambio Antes Ahora
Declaración public class Persona public abstract class Persona
Método actividad() Tenía cuerpo de relleno abstract, termina en ;
new Persona(...) Permitido Error de compilación
Hija sin actividad() Compilaba Error de compilación
Lo que NO cambia: los atributos protected, el constructor, mostrarDatos(), super(...) y @Override siguen funcionando exactamente igual. Las clases Empleado y Consultor casi no se tocan.

4. Ejercicio completo: paquete abstracto

Concepto que se demuestra: la Persona de la guía anterior se convierte en un molde que no se puede instanciar y que obliga a Empleado y Consultor a definir su propia actividad.

Clases necesarias: crea en NetBeans un paquete nuevo llamado abstracto con estos cuatro archivos. El último es el que ejecutarás.

Source Packages
      │
      └── abstracto
      ├── Persona.java          (clase abstracta)
      ├── Empleado.java         (clase hija)
      ├── Consultor.java        (clase hija)
      └── PruebaAbstracta.java  ← ejecuta este archivo
Cómo crear el paquete: clic derecho en Source Packages → New → Java Package, escribe abstracto y pulsa Finish. Luego, clic derecho en el paquete → New → Java Class por cada archivo.

4.1 Persona.java — la plantilla obligatoria

Persona.java 
package abstracto;

        // "abstract" significa: esta clase es solo un molde.
        // No se puede escribir new Persona(...) en ninguna parte.
        public abstract class Persona {

        // protected = visible dentro de esta clase y de sus hijas.
        protected int id;
        protected String dni;
        protected String nombre;
        protected String apellido;

        // Una clase abstracta SÍ tiene constructor.
        // No crea objetos de Persona: lo usan las hijas con super(...).
        public Persona(int id, String dni, String nombre, String apellido) {
        this.id = id;
        this.dni = dni;
        this.nombre = nombre;
        this.apellido = apellido;
        }

        // Método NORMAL: ya está resuelto y todas las hijas lo heredan.
        public void mostrarDatos() {
        System.out.println("ID: " + id);
        System.out.println("DNI: " + dni);
        System.out.println("Nombre: " + nombre + " " + apellido);
        }

        // Método ABSTRACTO: no tiene cuerpo, termina en punto y coma.
        // Toda clase hija está OBLIGADA a escribirlo.
        public abstract void actividad();
        }
Observa: la clase tiene atributos, constructor, un método resuelto y un método pendiente. Esa mezcla es justamente lo que define a una clase abstracta.

4.2 Empleado.java — cumple la obligación

Empleado.java 
package abstracto;

        // extends Persona = hereda todo Y acepta la obligación
        // de escribir el método abstracto actividad().
        public class Empleado extends Persona {

        private double sueldo;

        public Empleado(int id, String dni, String nombre,
        String apellido, double sueldo) {
        super(id, dni, nombre, apellido); // primera instrucción, siempre
        this.sueldo = sueldo;
        }

        public double getSueldo() {
        return sueldo;
        }

        // Si borras este método, la clase NO compila.
        @Override
        public void actividad() {
        System.out.println("El empleado trabaja en la empresa");
        }

        // Aquí sobrescribimos un método NORMAL, no uno abstracto.
        // super.mostrarDatos() conserva lo que ya hacía Persona.
        @Override
        public void mostrarDatos() {
        super.mostrarDatos();
        System.out.println("Sueldo: " + sueldo);
        }
        }

4.3 Consultor.java — la misma obligación, otra respuesta

Consultor.java 
package abstracto;

        public class Consultor extends Persona {

        private String nombreConsultora;

        public Consultor(int id, String dni, String nombre,
        String apellido, String nombreConsultora) {
        super(id, dni, nombre, apellido);
        this.nombreConsultora = nombreConsultora;
        }

        // Misma obligación que Empleado, respuesta diferente.
        // Eso es polimorfismo.
        @Override
        public void actividad() {
        System.out.println("El consultor brinda asesoría");
        }

        @Override
        public void mostrarDatos() {
        super.mostrarDatos();
        System.out.println("Consultora: " + nombreConsultora);
        }
        }

PruebaAbstracta.java ← ejecutar 
package abstracto;

        public class PruebaAbstracta {

        public static void main(String[] args) {

        // ERROR: Persona es abstracta, no se puede instanciar.
        // Persona p = new Persona(1, "12345678", "Ana", "Rojas");

        Empleado empleado = new Empleado(1, "23456789",
        "Carlos", "Pérez", 2500);

        Consultor consultor = new Consultor(2, "34567890",
        "Luis", "Torres", "Consultora ABC");

        empleado.mostrarDatos();
        empleado.actividad();

        System.out.println("------------------------");

        consultor.mostrarDatos();
        consultor.actividad();

        System.out.println("------------------------");

        // La referencia es de tipo Persona (la clase abstracta),
        // pero los objetos reales son Empleado y Consultor.
        Persona[] personas = { empleado, consultor };

        for (Persona persona : personas) {
        persona.actividad(); // cada objeto responde a su manera
        }

        System.out.println("------------------------");

        // El sueldo solo existe en Empleado, no en Persona.
        System.out.printf("Sueldo del empleado: %.2f%n", empleado.getSueldo());
        }
        }

Después, mostrarDatos() ejecuta la versión ampliada de cada hija —que empieza llamando a super.mostrarDatos()— y el bucle final recorre el arreglo Persona[] obteniendo dos respuestas distintas de la misma llamada.

5. Interfaces

La clase abstracta resolvió el problema de la obligación. Ahora aparece uno nuevo.

5.1 El problema que resuelve una interfaz

Imagina que la empresa también tiene máquinas que calculan un costo de operación. Una máquina no es una persona, así que no puede heredar de Persona. Pero sí queremos tratarla igual cuando calculamos pagos.

Limitación de Java: una clase solo puede tener un padre. class Maquina extends Persona, Equipo no existe en Java. La interfaz es la salida a este callejón.

5.2 ¿Qué es una interfaz?

Una interfaz es un contrato: una lista de métodos que una clase se compromete a escribir. No dice qué es la clase, dice qué sabe hacer.

Comparación sencilla: un carné de conducir no dice si eres médico o ingeniero. Solo certifica que sabes conducir. La interfaz es ese carné: certifica una capacidad, no una identidad.

5.3 ¿Para qué sirve?

  • Obligar a implementar un conjunto de métodos sin imponer una jerarquía de herencia.
  • Permitir que clases no emparentadas compartan un mismo tipo.
  • Rodear la limitación de un solo padre: una clase puede implementar varias interfaces.

5.4 Las palabras interface e implements

Concepto que se demuestra: dos clases sin ningún parentesco entre sí —un avión y un pájaro— pueden compartir el mismo tipo porque firman el mismo contrato.

Clases necesarias: crea el paquete volar con estos cuatro archivos.

Source Packages
      │
      └── volar
      ├── Volador.java        (interfaz)
      ├── Avion.java          (clase)
      ├── Pajaro.java         (clase)
      └── PruebaVolador.java  ← ejecuta este archivo
Volador.java 
package volar;

        // Un contrato con un solo compromiso.
        public interface Volador {
        void volar(); // sin cuerpo, sin la palabra abstract
        }
Avion.java 
package volar;

        public class Avion implements Volador {

        @Override
        public void volar() {
        System.out.println("El avión despega con motores");
        }
        }
Pajaro.java 
package volar;

        // Pajaro NO hereda de Avion ni comparte padre con él.
        // Lo único que tienen en común es saber volar.
        public class Pajaro implements Volador {

        @Override
        public void volar() {
        System.out.println("El pájaro vuela batiendo las alas");
        }
        }
Detalle importante: en una interfaz no hace falta escribir public ni abstract: los métodos ya son públicos y abstractos por definición. Pero en la clase que implementa, public sí es obligatorio.

▶ Ejecutar el ejemplo

Ejecuta este archivo: PruebaVolador.java.

PruebaVolador.java ← ejecutar 
package volar;

        public class PruebaVolador {

        public static void main(String[] args) {

        Avion avion = new Avion();
        Pajaro pajaro = new Pajaro();

        avion.volar();
        pajaro.volar();

        System.out.println("------------------------");

        // Una interfaz NO se instancia, pero SÍ sirve como tipo.
        // Volador v = new Volador(); // esto no compila

        Volador[] voladores = { avion, pajaro };

        for (Volador v : voladores) {
        v.volar();
        }

        System.out.println("Total de voladores: " + voladores.length);
        }
        }

Qué ocurre: Avion y Pajaro no tienen ninguna relación de herencia, pero ambos entran en el arreglo Volador[]. Eso es lo que una interfaz permite y la herencia no: agrupar clases que no son familia pero comparten una capacidad.

El pájaro vuela batiendo las alas

El pájaro vuela batiendo las alas
Total de voladores: 2

5.5 extends frente a implements

Aspecto extends implements
Se usa con Clases Interfaces
Significado «es un» «sabe hacer»
Cuántos se permiten Solo uno Varios, separados por coma
Hereda código Sí, atributos y métodos No, solo obligaciones

Para recordarlo: extends responde «¿qué soy?». implements responde «¿qué sé hacer?». Un Empleado es una Persona y sabe calcular su pago.

5.6 Varias interfaces a la vez

Concepto que se demuestra: una clase tiene un solo padre, pero puede firmar todos los contratos que necesite. Aquí un Tecnico sabe cobrar y además sabe generar un reporte.

Clases necesarias: crea el paquete variasinterfaces con cuatro archivos.

Source Packages
      │
      └── variasinterfaces
      ├── Cobrable.java        (interfaz 1)
      ├── Reportable.java      (interfaz 2)
      ├── Tecnico.java         (implementa las dos)
      └── PruebaVarias.java    ← ejecuta este archivo
Cobrable.java 
package variasinterfaces;

        public interface Cobrable {
        double calcularPago();
        }
Reportable.java 
package variasinterfaces;

        public interface Reportable {
        String generarReporte();
        }
Tecnico.java 
package variasinterfaces;

        // Dos interfaces separadas por coma.
        // La clase está obligada a escribir los métodos de AMBAS.
        public class Tecnico implements Cobrable, Reportable {

        private String nombre;
        private int servicios;

        public Tecnico(String nombre, int servicios) {
        this.nombre = nombre;
        this.servicios = servicios;
        }

        // Obligación de Cobrable.
        @Override
        public double calcularPago() {
        return servicios * 80;
        }

        // Obligación de Reportable.
        @Override
        public String generarReporte() {
        return "Técnico " + nombre + " atendió " + servicios + " servicios";
        }
        }
Orden obligatorio: si además heredas de una clase, primero extends y después implements: class Tecnico extends Persona implements Cobrable, Reportable. Escribirlo al revés es un error de compilación.

▶ Ejecutar el ejemplo

Ejecuta este archivo: PruebaVarias.java.

PruebaVarias.java ← ejecutar 
package variasinterfaces;

        public class PruebaVarias {

        public static void main(String[] args) {

        Tecnico tecnico = new Tecnico("Rosa Díaz", 7);

        // El objeto responde a los métodos de las dos interfaces.
        System.out.println(tecnico.generarReporte());
        System.out.printf("Pago: %.2f%n", tecnico.calcularPago());

        System.out.println("------------------------");

        // El MISMO objeto visto con dos tipos diferentes.
        Cobrable comoCobrable = tecnico;
        Reportable comoReportable = tecnico;

        System.out.printf("Solo el pago: %.2f%n", comoCobrable.calcularPago());
        System.out.println("Solo el reporte: " + comoReportable.generarReporte());
        }
        }

Qué ocurre: existe un solo objeto Tecnico en memoria. Las variables comoCobrable y comoReportable apuntan a él, pero cada una solo «ve» los métodos de su interfaz. Si escribes comoCobrable.generarReporte() el compilador lo rechaza, aunque el objeto real sepa hacerlo.

💻 Resultado esperado en consola

Técnico Rosa Díaz atendió 7 servicios
Pago: 560,00
------------------------
Solo el pago: 560,00
Solo el reporte: Técnico Rosa Díaz atendió 7 servicios

6. Ejercicio: paquete abstracto_interface

Concepto que se demuestra: una misma clase puede heredar de una clase abstracta y, al mismo tiempo, firmar el contrato de una interfaz. Empleado es una Persona y además sabe calcular su pago.

Clases necesarias: ampliamos el proyecto anterior con la interfaz Trabajable. Es el mismo ejemplo, un paso más adelante.

Source Packages
      │
      └── abstracto_interface
      ├── Persona.java          (clase abstracta)
      ├── Trabajable.java       (interfaz)
      ├── Empleado.java         (extends + implements)
      ├── Consultor.java        (extends + implements)
      └── PruebaInterface.java  ← ejecuta este archivo

6.1 Persona.java — sin cambios

Copia la misma clase abstracta del paquete anterior y cambia únicamente la primera línea:

Persona.java 
package abstracto_interface;

        public abstract class Persona {

        protected int id;
        protected String dni;
        protected String nombre;
        protected String apellido;

        public Persona(int id, String dni, String nombre, String apellido) {
        this.id = id;
        this.dni = dni;
        this.nombre = nombre;
        this.apellido = apellido;
        }

        public void mostrarDatos() {
        System.out.println("ID: " + id);
        System.out.println("DNI: " + dni);
        System.out.println("Nombre: " + nombre + " " + apellido);
        }

        public abstract void actividad();
        }

6.2 Trabajable.java — el contrato

En NetBeans: clic derecho en el paquete → New → Java Interface (no «Java Class»). Escribe Trabajable y pulsa Finish.
Trabajable.java 
package abstracto_interface;

        // Una interfaz NO es una clase: es una lista de compromisos.
        // No tiene atributos normales ni constructor.
        public interface Trabajable {

        // Todo lo que sea "trabajable" debe saber calcular su pago.
        double calcularPago();

        // Y debe saber mostrar su información completa.
        void mostrarInformacion();
        }
Observa: los dos métodos terminan en punto y coma, sin llaves. No escribimos public ni abstract: en una interfaz eso ya se da por hecho.

6.3 Empleado.java — hereda y firma el contrato

Empleado.java 
package abstracto_interface;

        // extends Persona -> ES una persona (hereda atributos y código)
        // implements Trabajable -> SABE trabajar (se obliga a 2 métodos más)
        public class Empleado extends Persona implements Trabajable {

        private double sueldo;
        private int horasExtra;

        public Empleado(int id, String dni, String nombre,
        String apellido, double sueldo, int horasExtra) {
        super(id, dni, nombre, apellido);
        this.sueldo = sueldo;
        this.horasExtra = horasExtra;
        }

        // --- Obligación que viene de la clase abstracta Persona ---
        @Override
        public void actividad() {
        System.out.println("El empleado trabaja en la empresa");
        }

        // --- Obligaciones que vienen de la interfaz Trabajable ---
        // Ojo: aquí "public" SÍ es obligatorio.
        @Override
        public double calcularPago() {
        return sueldo + (horasExtra * 20);
        }

        @Override
        public void mostrarInformacion() {
        mostrarDatos(); // heredado de Persona
        actividad(); // versión de Empleado
        System.out.println("Pago total: " + calcularPago());
        }
        }

6.4 Consultor.java — el mismo contrato, otro cálculo

Consultor.java 
package abstracto_interface;

        public class Consultor extends Persona implements Trabajable {

        private String nombreConsultora;
        private double tarifaHora;
        private int horas;

        public Consultor(int id, String dni, String nombre, String apellido,
        String nombreConsultora, double tarifaHora, int horas) {
        super(id, dni, nombre, apellido);
        this.nombreConsultora = nombreConsultora;
        this.tarifaHora = tarifaHora;
        this.horas = horas;
        }

        @Override
        public void actividad() {
        System.out.println("El consultor brinda asesoría");
        }

        // Mismo método, fórmula completamente distinta.
        @Override
        public double calcularPago() {
        return tarifaHora * horas;
        }

        @Override
        public void mostrarInformacion() {
        mostrarDatos();
        actividad();
        System.out.println("Consultora: " + nombreConsultora);
        System.out.println("Pago total: " + calcularPago());
        }
        }

PruebaInterface.java ← ejecutar

        public class PruebaInterface {

        public static void main(String[] args) {

        Empleado empleado = new Empleado(1, "23456789",
        "Carlos", "Pérez", 2500, 10);

        Consultor consultor = new Consultor(2, "34567890",
        "Luis", "Torres", "Consultora ABC", 150, 12);

        empleado.mostrarInformacion();
        System.out.println("------------------------");
        consultor.mostrarInformacion();
        System.out.println("------------------------");

        // Ahora el arreglo NO usa la clase, usa la INTERFAZ.
        // Solo importa que ambos sepan calcular su pago.
        Trabajable[] planilla = { empleado, consultor };

        double total = 0;
        for (Trabajable t : planilla) {
        // %-12s alinea el texto a la izquierda en 12 espacios.
        System.out.printf("%-12s %10.2f%n", "Pago:", t.calcularPago());
        total = total + t.calcularPago();
        }

        System.out.printf("%-12s %10.2f%n", "TOTAL:", total);
        }
        }

Qué ocurre: mostrarInformacion() viene de la interfaz, pero dentro llama a mostrarDatos() —heredado de la clase abstracta— y a actividad(), que es la versión propia de cada hija. Es decir: en un solo método se combinan la herencia, el polimorfismo y el contrato. El bucle final recorre Trabajable[] y suma pagos calculados con fórmulas distintas.

7. Comparación final

Esta tabla es el resumen que conviene memorizar.

Característica Clase normal Clase abstracta Interfaz
Se puede instanciar con new Sí No No
Puede tener atributos Sí Sí Solo constantes
Puede tener constructor Sí Sí (lo usa super) No
Métodos ya implementados Sí Sí No (en el nivel de este curso)
Métodos abstractos No Sí, opcionales Sí, todos lo son
Se usa con extends Sí Sí No
Se usa con implements No No Sí
Herencia múltiple No, un solo padre No, un solo padre Sí, varias interfaces
Sirve como tipo de referencia Sí Sí Sí
Responde a la pregunta «qué es y qué hace» «qué es» «qué sabe hacer»
Cómo decidir: si las clases comparten atributos y código, usa una clase abstracta. Si solo comparten capacidades y no están emparentadas, usa una interfaz. Se pueden combinar, como hicimos con Empleado extends Persona implements Trabajable.

9. Resumen

Concepto Java Finalidad
Clase abstracta abstract class Plantilla común que no se puede instanciar.
Método abstracto abstract void m(); Obligar a las hijas a escribir su versión.
Heredar extends Recibir atributos, código y obligaciones. Solo un padre.
Constructor padre super(...) Inicializar los atributos heredados.
Sobrescribir @Override Completar un método abstracto o reemplazar uno normal.
Interfaz interface Contrato de capacidades, sin código heredado.
Firmar el contrato implements Comprometerse a escribir los métodos. Varias a la vez.
Polimorfismo Tipo padre o interfaz Un mismo bucle, respuestas distintas por objeto.
Secuencia conceptual completa: clase normal → herencia con extends → sobrescritura con @Override → polimorfismo → clase abstracta con abstract → interfaz con implements.
La pregunta que decide todo: ¿la relación es «es un»? Usa extends con clase o clase abstracta. ¿Es «sabe hacer»? Usa implements con una interfaz. ¿Son las dos cosas? Úsalas juntas.
